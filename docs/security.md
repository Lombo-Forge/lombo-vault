This is the author's own threat model. There has been no independent review.

## What is protected

The contents of the archives: anyone who reads the backup folder without a private key sees only age-encrypted data. File **names and sizes** are visible in the manifest, which is not encrypted, so someone with the folder can see which paths exist and roughly how big they are, and can tell how often backups are made. The manifest also holds an unsalted **SHA-256 of every file**: a small, guessable file (a PIN, a short token alone in its own file) can be recovered from its hash by brute force. Do not rely on the backup folder being unreadable for such files; keep them out of the sources or accept the risk.

Encryption is done by the `age` program, not by this tool. LomboVault trusts age to do it right and checks only that age exited cleanly and that the output starts with an age header.

## What the drill proves, and what it does not

**It proves** (result `OK`) that the newest backup:

- exists, is recent, and its bytes match the checksum in the manifest;
- decrypts with the key file you named, and age's own integrity check of the whole file passes;
- unpacks, and every file in it has exactly the SHA-256 recorded when the backup was made, with nothing missing and nothing extra.

**It does not prove:**

- that the apps start from those files (the check is on bytes, not on behaviour; a database that was copied while being written has the right checksum and may still be corrupt);
- that the backup contains everything you need. Only the paths in `SOURCES` are in it;
- that the **manifest was not altered together with the archive**. Both live in the same folder and neither is signed. Someone who can write the folder could replace both. Age protects confidentiality; this tool does not defend against a writer of the backup folder (keep it write-protected from other services, and copy to a second place);
- that an older backup restores. Only the newest is drilled;
- that the key in your password manager is the same one as on the drill machine. Check that the one you would use in a disaster is the one that passes.
- anything about a `PARTIAL` result's hidden contents: it never decrypts.

## Key handling

- The private key is generated by `age-keygen` on a machine you trust. The tool never creates, stores or transmits it. `RECIPIENTS` takes public keys only and refuses anything that looks like a private key.
- `backup` never opens the key file. Only `drill` and `doctor` read `KEY_FILE`, locally.
- A private key on the same machine as the backups lets anyone with that machine's disk decrypt them. Choose between a drill on the server (convenient, weaker) and a drill on another machine that holds the key (stronger, needs a copy step). [setup.md](setup.md#4-first-drill) lays out both.
- `doctor` fails if the key file is inside the backup folder, warns if it is readable by other users, and checks that it opens a test message made for your recipients.
- Keep at least two copies of the private key in different places (password manager, printed in a safe). Several recipients let you keep a separate key per place.
- Never paste the private key into a chat, an issue or a webhook. Never commit it.

## If the key is lost

The backups cannot be opened. There is no recovery: not by the tool, not by age, not by the author. Anything you could do to "reset" it would be a weakness in the encryption.

What to do about it before it happens:

- Run `doctor` and the drill after every key change; the round-trip check proves the key you hold opens a backup made for your recipients.
- Keep a second recipient with a key stored elsewhere.
- If you only notice after the loss, make a new key pair, change `RECIPIENTS`, and take a new backup from the live data straight away. The old backups are only useful if the old key turns up.

## Other risks

- **Attacker with write access to the backup folder** can delete backups or replace them (see above). Retention will not delete anything unless a complete newer one exists, but a replaced "newest" backup is the one retention counts on.
- **Attacker with the public key** can make backups that look right but contain anything; encryption to a public key proves nothing about the author.
- **The webhook URL and ping URLs are secrets** in practice (anyone with a ping URL can fake a success). They live in the environment, and must not be committed. The tool never prints them: a failed alert or ping reports only the kind of failure (for example `ping failed (InvalidURL)`), and an address with a space or control character is refused at start-up.
- **Source data is read as the user running the tool.** Running as root gets everything, but also means a bug is a root bug. Prefer a user with read access to the specific folders.
- **Restoring from an untrusted archive.** The drill unpacks with tarfile's `tar` filter that refuses members that would land outside the scratch folder; the archive is only trusted as far as the holder of your key and recipients. Do not run the drill on archives you did not make. Anyone who can write to the backup folder can also write a manifest, so the drill stops unpacking once the archive holds more bytes than the manifest says (plus 1 MB) and fails on any member that is not a file, folder or link. Links, empty folders and file modes are still not compared.
- **A wrong clock.** Order and age come from the time in the file name. Backups dated more than a day ahead are never counted by retention and make the drill fail; a clock far in the past makes new backups look old, and the drill's age check then fails.
- **The newest backup is only checked by the drill.** Retention counts a run as complete when both its files exist; if the newest one is damaged, each later run still deletes an older good one once `KEEP` is exceeded. Run the drill often relative to `KEEP`.
- **The scratch folder briefly holds a decrypted copy of your data.** It is created with mode 0700, under `SCRATCH_DIR` (set it to an encrypted or private disk) and removed afterwards, also on failure. If the machine crashes mid-drill, a `lombovault-drill-*` folder may remain: delete it.

## The same-disk check

`backup`, `plan` and `doctor` compare the device id (`st_dev`) of every source with the device id of the backup folder (or, if it does not exist yet, of its nearest existing parent). If one matches, `backup` writes nothing and says so, and `doctor` shows FAIL: a backup on the disk that holds the data is lost together with the data. `LOMBO_VAULT_ALLOW_SAME_DISK=true` turns the check off for a person who knows better (for example two partitions they trust to fail separately, or a test).

What the check **cannot see**, because the operating system reports one device id for what are really two disks, or different ids for one:

- network shares (NFS, SMB) and FUSE mounts, which often report one id for the whole share;
- bind mounts and container volume mounts, which can show the same id for a host folder and the disk behind it;
- overlay filesystems (a container's own filesystem), which report one id for many layers and disks;
- a pool such as mergerfs or a RAID or LVM volume: one id for the pool, however many disks sit behind it. Two folders in the same pool pass or fail together, and the check cannot tell whether the data and the backup land on the same member disk;
- two partitions of one physical disk: different ids, so it passes although one failing disk takes both.

Only the source path itself is compared, not mounts inside a source folder. The check errs on the side of warning: when the ids match it refuses even if the disks differ, and when it cannot read a device id it also refuses. It never reads or changes file contents, and it logs only the folder names you configured.

## How the tool limits damage

- Deletion is limited to the tool's own file names, checked twice, and only after a successful backup, and only with `DRY_RUN=false`.
- A source cannot overlap the backup folder, so the tool cannot back up or delete its own output through a source.
- A failed backup leaves nothing half-written under a real name.
- The tool is standard library only; it runs the `age` binary with a fixed argument list (no shell).
